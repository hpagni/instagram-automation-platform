# Architecture

This document describes the full system at a high level so the scale and the engineering are clear, then marks which parts are published here and which are described only. The goal is to convey the shape of a real distributed system, not to provide a recipe for operating accounts against a platform's terms of service.

## The problem

Operate a large fleet of Instagram accounts and their content at the same time from a small number of Linux hosts. Each account needs its own browser session, its own network identity, and a steady supply of generated content. The work is bursty, memory-heavy (each browser session is several hundred megabytes resident), and failure-prone (a session can crash mid-task), so the system has to admit work carefully, isolate accounts from each other, and recover jobs that die.

## System overview

The system is a set of long-running worker processes on top of a durable job queue, feeding a fleet of isolated browser sessions, with an AI pipeline producing the content those sessions post, and a monitor watching the whole thing.

```
                         +------------------------+
                         |   Durable job queue    |   (distributed-job-runner)
                         |  lease-based, retried  |
                         +-----------+------------+
                                     |
                lease jobs           |          dispatch
        +----------------------------+----------------------------+
        |                            |                            |
   +----v-----+                 +----v-----+                 +----v-----+
   | worker 1 |       ...       | worker N |                 | monitor  |
   +----+-----+                 +----+-----+                 +----------+
        |                            |
   two-tier concurrency admission (per-session mutex + box-wide cap)
        |                            |
   +----v----------------------------v----+
   |   isolated per-account browser        |
   |   sessions, each pinned to a proxy    |
   +----+----------------------------------+
        |
   +----v---------+     +------------------+
   | proxy pool   |     | AI content       |
   | + geo lookup |     | pipeline (LLM     |
   +--------------+     | captions + images)|
                        +------------------+
```

### (a) Isolated per-account browser sessions

Every account runs in its own browser session with its own on-disk profile directory, and each session is pinned to its own proxy so accounts do not share a network identity. Two processes must never open the same profile directory at once, because concurrent access corrupts the session's local stores. That constraint is enforced by the per-session queue described below.

The proxy pool and the IP geolocation resolver that supports it are published here (`src/proxy/`). The proxy client lists ISP proxies from a provider API and returns ready-to-use proxy URLs; the geo resolver maps an IP to its city, timezone, and coordinates.

### (b) Durable lease-based job queue over a PM2 worker fleet

Browser work is not run inline. It is enqueued as jobs and leased by workers. A worker takes a lease on a job, does the work, and marks it done; if the worker dies, the lease expires and the job becomes available again, so no work is silently lost. This durable, lease-based queue is the backbone of the system and is published on its own as [distributed-job-runner](https://github.com/hpagni/distributed-job-runner).

The workers run under PM2 as a fleet (`ecosystem.config.js`). Scaling is a matter of raising the worker count. Because each browser session is expensive, work is admitted through two tiers of concurrency control, both published here:

- Per-session serialization (`src/queue/profile-queue.js`, `src/queue/session-queue.js`). A cross-process file-based mutex keyed by session id, so only one worker touches a given account at a time, with a cooldown gap between consecutive holders. It takes over stale locks when a holder process has died.
- Box-wide admission (`src/concurrency/global-cap.js`). A file-based FIFO semaphore, partitioned into pools, that caps how many sessions run concurrently on a host. On top of the hard cap it applies a resource-admission gate: it refuses to start another session when free memory is below a watermark or CPU load is above a ratio, and backs off until pressure clears. This is the backpressure that keeps a host from running itself out of memory.

A pacing helper (`src/concurrency/throttle.js`) spreads out clicks within a session, and a scheduler cooldown budget (`src/concurrency/scheduler-budget.js`) lets a dispatcher avoid reusing the same resource key too often within a window.

### (c) AI content-generation pipeline

Posts are generated. The pipeline produces a caption and an image for each post. Captions are generated by an LLM steered with a system prompt and a fresh sample of few-shot exemplars per call, then the best candidate is selected. Images are generated from a scene description. Every generator exposes a short hash of its prompt text, so any output can be traced back to the exact prompt version that produced it and prompt edits can be correlated against quality changes.

The content clients are published here (`src/content/`): wrappers for OpenAI, Anthropic, and Gemini, each with retry and exponential backoff on transient errors. A vision-LLM action fallback (`src/content/ai-fallback.js`) is a resilience layer for the browser automation: when a normal selector-based click fails because the page layout changed, it screenshots the page, lists the visible interactive elements, asks a vision model which one matches the intent, and clicks it. In the published clients these generators have been decoupled from the persona and likeness generation that the private system used to drive them (see below).

### (d) Engagement and audience statistics

The private system collected engagement and audience statistics across the account network and tracked them over time. This box is named here for completeness. Its implementation, including the scraping of follower and engagement data and the automated following behavior, is omitted from the public release. No method-level detail is provided.

### (e) Monitoring and crash recovery

A monitor process runs alongside the workers. It watches queue depth and worker health and surfaces problems. The PM2 layer restarts crashed workers with a bounded restart count so a persistent fault does not spin, and memory caps trigger a restart before a leaking process takes a host down. The queue's lease expiry handles the other half of recovery: a job whose worker died is retried by another worker.

## Components described but not published

Two subsystems are core to how the full system worked but are deliberately left out of this release. They are named here as architectural boxes with a single sentence each, and no implementation detail.

- Account provisioning. The subsystem that created and registered accounts and carried out the identity, phone, and email verification steps that provisioning required. Implementation omitted.
- Session integrity. The subsystem responsible for making automated browser sessions behave like ordinary browser traffic, including any challenge handling. Implementation omitted.

Alongside those, several supporting pieces are omitted for the same reason: the persona and likeness generation that fabricated per-account identities and reference imagery, and the account-network data collection described in (d).

## Why these omissions

The included code is useful and coherent on its own as general infrastructure: a durable queue, two-tier concurrency control with resource backpressure, a proxy pool, and multi-provider AI content clients are all things you would build for many kinds of large-scale browser automation. The omitted subsystems exist only to operate accounts against Instagram's terms of service, so republishing or improving them would do harm with no general engineering value. They are described here only at the level needed to understand the system's shape.

## A second proxy provider client

The private system carried a second proxy client for a rotating-residential provider. It is omitted here because it was not a plain proxy-list client: it built per-session sticky gateway credentials whose purpose was tied to the provisioning flow rather than to general proxy use. The included IPRoyal client is a straightforward list-and-format client and is representative of the neutral proxy layer.
